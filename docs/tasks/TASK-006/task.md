## 4. 报价生命周期和审批

可以沿用 api-conventions 的命名，但需区分可编辑草稿、不可变审批候选、不可变发布内容与可变化的生命周期状态。

最小行为：草稿 → 提交审批 → 待审批 → 批准/驳回；批准且仍有效 → 发布。待审批或批准后允许修改草稿，但必须使原审批失效并要求重新提交。发布后修订产生独立草稿版本，不原位编辑发布内容。

- 提交时后端重算并冻结审批候选：草稿版本、配置、客户/项目必要信息、报价有效期、价格、金额、折扣、规则、风险及政策版本。生成稳定、规范化内容 hash；不包含请求时间等无业务意义噪声。
- 审批记录绑定候选 id/version/hash、审批人、结论、说明、风险确认和时间。历史审批不删除、不覆写成新审批。
- 首期全部报价需要人工审批，且审批人不能是该次提交人。用两名不同虚构身份完成测试；单人企业没有第二人时显示待分配审批，不暗中自批。
- 默认 member/admin 可提交本人有权访问客户的草稿，admin 可审批及发布，viewer 只读；服务端定义独立 permission，不只依赖按钮或前端角色判断。
- 提交人、审批人和发布人的客户访问权、membership、企业上下文均须实时检查。幂等重放仍检查当前访问权限。
- 配置、数量、客户/项目、报价有效期、金额/价格依据、折扣或发布政策等审批相关内容变化后，旧审批不可继续用于发布。
- 发布时同一事务重新校验依赖和当前内容 hash；不一致返回明确冲突/需重新审批，不能默默替换成新金额发布。
- 时间自然流逝不应无故改变 hash，但跨价格/折扣/报价有效期必须触发相应失效判断。
- 审批决定重复提交需幂等；并发批准/驳回只能形成一个有效终局，不出现同时批准和驳回。

## 5. 不可变发布版本

- 人工点击发布并确认后，后端生成独立 quote_version 及唯一租户内编号/修订号，关联草稿和有效审批。
- 快照包括客户/项目必要展示信息、设备配置、模板与规则版本、商业行/数量、价格来源、币种及口径、折扣、总额、未知字段、风险确认、发布政策及审批引用、发布时间与有效期。
- 已发布内容既受 API 限制，也受数据库权限/约束或触发器保护。直接使用运行角色 UPDATE/DELETE 不得改写发布内容。
- 报价撤回/过期状态与冻结内容分离，保留事件历史；撤回要求权限、原因、幂等和并发控制。
- 过期采用 [issued_at, valid_until)；服务端所有消费入口都实时判断，不依赖页面时钟或后台任务及时运行。
- 客户、SKU、价格表、政策后续变化不改写已发布内容。详情展示冻结值，当前变化可单独提示，不以实时关联替换历史。
- 发布重试不重复编号或版本；同一审批候选不能借不同幂等键重复发布。
- 允许由发布版本创建修订草稿，保留来源链并重新检查当前引用与价格；旧审批不继承。

## 6. 从报价生成合同草稿

- 仅从本企业、当前有权访问且未撤回/过期的已发布报价版本生成。
- 固定来源 quote_version_id 和快照 hash；商业内容直接复制冻结报价，禁止重新读取最新价重新计算。
- 本轮规定每个已发布报价版本最多对应一个来源合同草稿，数据库唯一约束加服务端幂等双重防重；不同请求键、并发请求同样不重复。
- 合同草稿展示：甲方名称与地址（若已有）、项目/联系人信息（若已有）、乙方企业资料（若已配置）、销售/售后责任人（若已有）、设备及品牌属性、数量、报价金额/口径、来源版本及审批发布信息。
- 缺失字段明确待补齐，不从姓名猜测负责人，不把乙方登录人默认当销售或运维责任人。成本、内部审批说明等敏感信息继续按权限控制。
- 数据按来源复制为草稿字段，不建立会随 CRM 变化自动改写的展示关系；记录字段来源及复制时点。
- 本轮只实现创建、列表、详情及来源追溯。完整甲乙方编辑、付款节点、附件、签约和订单归 TASK-007。
- 生成合同草稿不等于客户接受报价、签约、收入确认或折扣核销。
- 若生成后源报价被撤回/过期，保留合同草稿和来源，显示警示；后续签约资格由 TASK-007 明确验证。本轮不自动删除草稿。
