## R1 — P2：设备查询页面新增强制交付权限，破坏原设备查询授权

位置：

- `apps/web/src/Assembly.tsx` 第 23 行：`load()` 无条件将设备查询从 `/assembly/devices` 改为 `/delivery/devices`。
- 同文件第 45、47 行：详情和搜索也切换到新接口。
- `apps/api/src/silicon/assembly/routes.py` 第 57–64 行：原设备接口以 `device.read` 授权。
- `apps/api/src/silicon/delivery/routes.py` 第 21–30 行：新设备接口统一以 `delivery.read` 授权。

### 触发条件与影响

用户保留 `device.read`、`inventory.read`（装配页面还可拥有 `assembly.read`），但不具备 `delivery.read`。例如只负责设备查询的人员，或角色的交付查询权限被撤销。

原设备接口仍允许查询，但“设备查询”页面现在请求交付接口并收到 403，失去原本已授权的设备列表、搜索和详情。装配页面复用了同一个 `load()`，且在设备请求返回前不提交已取得的工单数据，因此同一权限组合也会使装配页面的初始聚合加载失败。

默认 admin/member/viewer 迁移时同时获得这些查询权限，所以现有默认角色测试和普通浏览器闭环没有暴露该问题。项目已经支持细粒度权限校验及撤权回归，不能仅按三个默认角色同时拥有权限来判断兼容性。

### 独立定向复现

使用真实 FastAPI 路由和 TestClient，替换身份/持久化边界，按给定权限集合执行实际路由权限选择；列表持久化返回空集合，避免将此探针描述为真实数据库测试。

权限集合：`assembly.read`、`device.read`、`inventory.read`，不含 `delivery.read`。

| 请求 | 结果 |
| --- | --- |
| `GET /api/v1/assembly/devices` | 200 |
| `GET /api/v1/delivery/devices` | 403 |

页面源码进一步确认：设备列表、搜索和详情全部使用第二个接口，未按权限选择原设备查询入口。

### 修复要求

保留原 `device.read` 对基础设备查询的授权能力。交付历史可根据 `delivery.read` 作为增强数据加载；或建立明确的分层响应与授权方案，使设备查询及装配页面不因缺少无关交付查询权限整体失败。

不得通过删除服务端权限检查、默认给所有人扩大交付权限，或在请求失败后用假数据掩盖问题。只有交付查询权限的用户可以看到哪些基础设备字段，也应在同一方案中明确，避免修改时意外扩大其他领域权限。

最低回归验收：

1. 有 `device.read`、无 `delivery.read`：原设备列表、搜索和详情可用；未授权的交付信息不可见。
2. 有装配及设备查询权限、无交付查询权限：装配列表与已授权操作正常加载。
3. 两类查询权限均有：设备信息和交付历史正常显示。
4. 交付权限被撤销或请求返回 403：保留可用的基础设备查询，清除已无权展示的交付数据。
5. 跨租户和成本字段裁剪继续有效。

至少补一项真实权限/API 回归和一项实际 React 页面回归，不只检查按钮或路径字符串。
