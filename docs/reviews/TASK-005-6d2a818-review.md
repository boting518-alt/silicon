## R1 · P2：已选可选部件没有进入实际配置的兼容检查

位置：`apps/api/src/silicon/quotes/service.py` 第 57–74 行；关联 `apps/api/src/silicon/catalog/service.py` 的 checks。

报价根据 excluded_sku_ids 决定技术部件是否选中，但 preview 保留了 BOM 的 required 标记。catalog.checks 只检查 required=True 的行，selected_categories 也只统计这部分行。因此，BOM 中标为可选、但当前报价已经选中且实际计费的部件会被排除在 CPU/内存/电源检查之外。

可复现条件：

1. 创建示例平台规则，CPU 插槽为 A。
2. 发布一个 BOM：必选 CPU-A，插槽 A；可选 CPU-B，插槽 B，两者 charge_mode 均为 separate。
3. 创建报价，两项都保持选中，不排除任何 SKU，并配置有效价格。
4. 后端将 CPU-B 计入商业行和金额，但 socket 检查返回 PASS，只检查了 CPU-A。

Reviewer 使用实际 evaluate 与 catalog.checks 执行定向探针，替换仓储读取及客户访问依赖。结果确认 CPU-B 被计价，而 socket 返回 `PASS / CPU 插槽符合所选示例资料（非完整认证）`。该探针不是 HTTP/真实数据库测试。

影响：已经具备资料、可以识别的不匹配被错误显示为单项 PASS。sale_ready=false 和整体 UNKNOWN 限制了后续发布，但不能纠正这条局部检查的错误。类似地，已选可选电源可能仍被报告为没有必选电源。

修复要求：

- 区分“模板必选性”与“当前配置是否已选”。兼容计算应覆盖当前实际选中的部件；类别完整性应按当前选中配置判断，同时保留模板必选类别要求。
- 保留原 BOM 元数据和历史快照；不要通过全局改变目录 checks 的语义破坏 TASK-004 对未选可选件的处理。
- 增加真实 PG/API 回归：已选可选不匹配 CPU/内存必须 BLOCK；排除该可选件后不再参与；已选可选电源参与容量判断。至少覆盖原必选件与可选件混合的场景，避免只测所有行 required=True。

## R2 · P2：新建相同草稿复用上一次创建的幂等键

位置：`apps/web/src/QuoteStudio.tsx` 的 key ref、save（第 24 行）和“新建草稿”事件（第 31 行）。

save 仅在 payload 的 JSON signature 改变时生成新幂等键。“新建草稿”清理了 form/saved 等状态，却没有重新建立创建操作的幂等身份。

可复现条件：

1. 在报价页面保存一份新草稿。
2. 不离开页面，点击“新建草稿”。
3. 填入相同名称、客户、项目及完全相同的配置，再保存。
4. 第二次 POST /quotes 的 payload 和 Idempotency-Key 均与第一次相同。后端按正确的重放逻辑返回第一份草稿，因此没有创建第二份；页面却显示“草稿已保存”。

Reviewer 将实际 TSX 转译后，在 hook/请求替身环境中执行真实保存和新建事件处理器，确认两次有意创建发出的幂等键相同。后端 service.save 对相同 key/hash 返回 prior.response 的路径已核对。未以该组件探针冒充浏览器或数据库端到端复现。

影响：用户的新建意图被误判为网络重试，第二份草稿没有创建；接下来编辑可能修改原草稿。该问题与配置是否允许重复无关：当前接口允许不同创建命令产生相同内容的独立草稿。

修复要求：

- 在显式“新建草稿”时重置创建操作的幂等身份，必要时将本地草稿会话标识纳入命令身份。
- 同一次保存的网络重试仍应复用原幂等键，不能简单改成每次点击保存都生成新键。
- 增加组件/浏览器回归：相同内容连续新建得到不同 draft_id；同一创建请求重试只产生一份；保留并发编辑 expected_version 测试。
