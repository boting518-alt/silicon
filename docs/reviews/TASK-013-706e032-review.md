## R1 · P2 · 无交付权限仍通过指标说明泄漏完工/待发数量

位置：`apps/api/src/silicon/analytics/service.py`，`Projection.metric` 及 `delivery`，尤其第 139 行。

`delivery()` 先计算样本和待发数量，再把它们拼入 `basis`。`metric()` 在缺少 `delivery.read` 时清空 value、groups、明细并覆盖 reason，却保留该动态 basis。前端的口径按钮可显示它，API 本身也返回它。

独立函数级复现：身份只有 analytics.read、all 数据范围；一个可关联客户的订单，有一个有效完工且尚未发货。调用交付投影后返回：

```json
{
  "id": "completion_to_ship",
  "value": null,
  "status": "unauthorized",
  "reason": "没有来源数据权限",
  "basis": "经营样本0个；未发1个；非财务周转率",
  "drillable": false,
  "groups": []
}
```

这违反来源领域权限约束。禁止下钻不能补救概览中已经披露的数量。

修复要求：无来源权限时只能返回不含业务事实的通用口径。检查所有元数据字段，包括 basis、reason、标题、注释及派生说明，不能仅清空 value。无需扩大角色权限。

验收：真实 API 使用有 analytics.read、无 delivery.read 的身份，分别准备不同已发/未发样本，响应及口径弹窗均不能暴露样本数或待发数；授权用户仍能看到正确样本解释。保留行级范围、撤权与明细鉴权测试。

## R2 · P2 · 期间资金流量被余额截止日隐式截断

位置：同文件 `finance()` 第 159–165、197–201 行，以及 receipts/payments/refunds/net_cash 指标。

任务书要求期间流量与截止日余额分开。当前资金流量调用复用于余额的 `confirmed()`，该函数要求确认日期不晚于 as_of；流量的逆向记录也额外受 as_of 限制。合同与发货期间指标却按 start/end 计算。于是同一页“本期”指标使用不同的实际时间范围，返回值仍标为 complete。

独立函数级复现，调用实际 `Projection.finance()`：

- 固定期间 `[2026-01-01, 2026-03-01)`。
- 一笔 100.00 元实际收款，2026-02-10 发生并确认，全部历史元数据齐全。
- as_of=2026-01-31：receipts 返回 `0.00 / complete`。
- 仅改 as_of=2026-02-28：receipts 返回 `100.00 / complete`。

按本轮已约定口径，这两次期间实际收款应同为 100.00；截止日未分配余额可以分别为 0 和 100。固定期间内的退款及逆向事实也应遵循期间规则，不能因余额截止日变化而被遗漏。

修复要求：分离期间流量的事实纳入规则与截止日余额重建规则。按查询时已知的有效确认事实、发生日期及各逆向日期计算期间流量；余额继续按 as_of 重建。分别评估相应指标的历史完整性，避免一个无关计划缺确认时间导致全部期间现金指标不可用。保持原始资金事实及确认时间不可变。不要通过偷偷联动或限制筛选日期、仅更改标签来掩盖口径冲突。

验收：真实 PG/API 固定期间，分别选择期间之前、期间中、期间末的 as_of，验证期间收款/付款/两类退款/净现金流保持一致，而余额随截止日正确变化；覆盖跨期原款与逆向、事后登记的历史发生日期、缺失确认元数据。图表与下钻同源对账。现有历史测试把资金期间总额与 as_of 绑定，应按正确业务口径调整，不能保留错误断言只补新测试。
