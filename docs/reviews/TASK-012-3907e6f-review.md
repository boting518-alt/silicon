## R1 — P2：同层分批返回并继续隔离后，逐明细最终处置被错误拒绝

位置：`apps/api/src/silicon/service/service.py`，`dispose()` 第 385 行起，关键校验在第 400 行。

代码按返回明细取得本次 quantity，但要求隔离库存的一整条余额恰好等于该数量：

```python
balance = next((x for x in balances_for(db, layer)
                if x['state'] == 'quarantine'
                and x['quantity'] == quantity), None)
```

### 合法业务路径

1. 一项批次追踪的旧安装包含 2 件，换件后原旧件作为同一客户保管层进入隔离。
2. 将这 2 件送出 RMA。
3. 原件修复分两次返回，每次 1 件，返回到同一个库位。
4. 两条返回记录分别检验并选择 `hold`，继续隔离。
5. 同一个 layer/location/state 的库存余额合并为 2 件。
6. 选择任一返回明细最终归还客户或有据报废，本次处置数量为 1。

实际：2 != 1，返回 `SERVICE_PART_DEPENDENCY`；两条明细都不能正常完成最终处置。

预期：在验证该返回明细尚未处置、关联正确且可处置余额足够的前提下，允许消费该明细的 1 件。第一次后剩余隔离 1 件，第二次后为 0，各自保存完整处置关系。

这是正常的分批返回与隔离合并场景，不应要求用户人为拆库位或调整库存才能结束流程。

### 独立复现与证据边界

调用真实 `dispose()` 函数，以持久化读取替身提供：同工单的返回明细 quantity=1、已有 hold 检验、无既有处置，以及对应隔离余额 quantity=2。实际触发 `SERVICE_PART_DEPENDENCY`。

探针第一次因测试夹具漏填返回记录 id 失败，补齐后复现上述业务判断；该准备错误不计为产品缺陷。最终探针不是 PostgreSQL/API 测试，不验证数据库锁与事务。

源码同时确认 `rma_return(kind='repair')` 复用原层，`rma_inspect(disposition='hold')` 将数量移入同层同库位 quarantine，因此上述余额合并符合实现路径。

现有测试覆盖“多行各返回一件”和“单件 hold 后处置”，但未覆盖“同一行数量多件、分批返回、同层同库位两次 hold 后分别处置”。

### 修复要求

- 将返回明细尚未处置的数量和库存聚合余额分开校验，允许余额足够时按合法明细消耗。
- 不仅放宽比较符号：继续验证租户、工单、RMA/返回关系、hold 检验及未处置状态，保留唯一处置约束和事务锁。
- 明确多个库位时的定位/分配规则，不能随意消费不属于目标保管事实的数量。
- 原退货、检验、库存层及处置历史不可删除或改写。

最低回归：

1. 同批次 2 件 → 同行分两次各返 1 件 → 同库位各 hold → 分别处置成功，隔离余额 2→1→0。
2. 一条归还客户、另一条报废，两种去向独立可追溯，所有权与公司库存价值不混淆。
3. 同一返回记录重复/并发处置只能一次生效。
4. 两条不同返回记录并发处置不超扣库存，最终余额为 0。
5. 余额不足、跨工单/跨租户、尚未 hold 检验时正确拒绝。
6. 原单件处置、多行 RMA 返回、旧件直接处置和库存对账继续通过。
