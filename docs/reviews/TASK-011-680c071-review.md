## R1 — P2：负向金额调整无法在原额度内更正恢复

位置：`apps/api/src/silicon/finance/service.py`

- `occupied()`，第 124 行起：累计原确认金额，加上所有正向调整；负向调整不减少占用。
- `adjust()`，第 181 行起：所有正向调整都要求 `occupied + 本次金额 <= 来源额度`。
- `source_adjustment()`，第 222 行起：来源额度调整也受该占用口径约束。

### 最小场景

1. 合同可登记额度为 1,000 元。
2. 确认一项 1,000 元应收，没有核销或其他下游依赖。
3. 经办人误登记 -200 元调整，应收有效金额变为 800 元。
4. 发现错误，追加 +200 元以恢复原约定金额。

预期：通过明确关联原错误调整的受控更正，恢复有效应收至 1,000 元，保留历史；来源合同额度仍为 1,000 元。

实际：`occupied()` 仍为 1,000，`adjust()` 将恢复金额计为新增占用，按 1,000 + 200 > 1,000 拒绝，返回 `FIN_SOURCE_CAP_EXCEEDED`。

本次以真实 `occupied()` SQL 和真实 `adjust()` 函数做了定向复现：SQLite 内存表保存原计划和 -200 调整，注册等价的二参数 greatest 函数；计划投影及来源读取使用替身。实际输出为：

```text
original=1000, adjustment=-200, effective=800,
attempted correction=+200, source_cap=1000
actual occupied SQL=1000
actual adjust result=FIN_SOURCE_CAP_EXCEEDED
```

该探针验证确定性金额判断，不是 PostgreSQL/API 集成测试，也不证明并发或 RLS 行为。

### 影响与原因

这不只是禁止重复生成新计划：同一计划的误减恢复也被禁止。现有调整表不可改写，逆向类型仅覆盖核销、资金、退款、发票，未提供针对计划调整的逆向/更正关系，因此用户没有保持真实合同额度的修复路径。

若先把来源额度虚增 200 才能恢复，则来源变为 1,200；恢复后累计正向占用同样为 1,200，来源额度也无法直接降回 1,000。不能用虚构商务增额解决录入错误。应付方向存在相同问题。

ADR-016 中“减少不释放重复生成空间”的目的合理，但需要区分新增债权额度与对既有错误调整的恢复，不能让防重复规则阻断合法更正。

现有测试覆盖负向调整、退款和退款冲销，但未覆盖负向调整自身的错误更正闭环。

### 修复要求

1. 提供显式、可追溯的调整更正或逆向路径，关联原调整，限定同租户、同计划及合法来源。
2. 正确计算有效调整与额度占用：原额度内的错误恢复不需要增加合同额度。
3. 保留“负向业务调整不能被用来重复生成原合同债权”的保护，不简单把所有负数全局抵扣后放开新计划。
4. 防止同一错误调整被重复或并发恢复；需要支持部分恢复时，累计不得超过可恢复金额。
5. 继续校验有效金额非负且不低于有效核销；涉及退款或其他下游事实时明确处理顺序。
6. 页面提供明确更正入口或流程，显示原调整、修复关系及有效金额，不提示用户虚增商业额度。
7. 更新 ADR、契约及对账口径；若新增字段/约束，使用兼容迁移保留原历史。

最低回归：

- 应收和应付的“1,000 → 误减 200 → 恢复 200”，合同额度始终 1,000。
- 更正后继续核销与对账，金额守恒。
- 重复/并发恢复只有合法总额生效，幂等重放不重复。
- 真实减额后仍不能借此重复生成原合同债权。
- 原调整跨租户、跨计划引用及无更正权限被拒绝。
- 真实退货关联调整的更正规则可解释，原退货防重保护保留。

至少补充真实 PG/API 定向回归，并通过页面完成一次误减恢复，不只测试算式。
