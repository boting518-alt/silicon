# ADR-008：页面企业上下文与客户聚合读取

状态：TASK-003 R1/R2 修复，review_ready，待独立复核。基线 45453c72ac2ab52a1e1375982256b1da70c0ef09。

## R1：上下文声明，不是授权

所有 CRM 路由（包括成员、列表、详情、创建和修改）要求两个 Header：X-Expected-Tenant 为页面绑定的 tenant_id；X-Session-Context 为 GET /session 返回的 context_id。后者是随机 UUID、不是令牌或授权凭据，不能由它反查/建立会话。真正身份仍由 Secure/HttpOnly 会话 Cookie、有效用户/membership、操作权限和 RLS 决定。写请求继续验证 Origin/CSRF。

0004_session_context 为既有 sessions 填充非空随机 context_id。新登录建立新会话/新上下文；每次显式选择企业都轮换，包括 A→B→A 和重新选择 A。因此不能只比较 tenant_id，也不能把旧表单自动绑定到后来相同企业的新上下文。

缺 Header 返回 428/CONTEXT_REQUIRED，不匹配返回 409/CONTEXT_CHANGED；均是稳定错误、回滚并审计拒绝，不向当前企业改投、不自动重试。未登录仍为 401，真实授权失败仍为 403，匹配上下文后的不可见客户为 404。契约已进入生成的 OpenAPI/客户端类型。历史客户端不具备此声明，必须刷新，不提供兼容旁路。

## 与切企业的顺序

沿用 authenticated 的 sessions FOR UPDATE 锁；request_tenant 在同一事务持锁核验两个 Header，再做 membership/权限/租户 GUC 和业务操作，直至提交/回滚才释放。select_tenant 使用同一会话锁后更新 tenant/context_id。不存在“先检查，再另开事务按新企业执行”。

两种可接受顺序：

1. 保存先持锁：保存到声明的 A 并提交，之后切 B。即使 A 的成功响应晚到，前端也会丢弃失效代次的结果；没有把保存转投 B。
2. 切企业先持锁：先提交 B/新 context_id；旧 A 请求醒来看到更新后的会话，返回 409，业务写入不发生。

主要锁顺序为 session → 身份/membership 共享锁 → 幂等事务锁（写）→ 客户父锁 → 子项。切企业到 membership 为止，不取得客户锁。内部受信服务不模拟页面 Header，继续显式授权 tenant_transaction；不能由任意 payload 指定租户。没有改变 Worker 任务语义。

## 前端失效与成功响应竞态

每个 CRM 调用捕获不可变的企业、context_id、请求代次和取消信号；在发送前与 JSON 成功返回后检查代次，不能把尚未结束的调用重新绑定到最新会话。列表、详情与新建/编辑全部经过同一 CrmRequests 边界；React 的列表取消和 onSaved/详情代次校验继续保留。

切换/收到跨标签通知会清空数据、详情、表单、搜索/分页及在途状态，把企业选择置空并明确提示重新选择。BroadcastChannel 带标签 sender 排除自身；storage 事件作补充，不写入客户正文、令牌或草稿。窗口 focus / visibility 恢复时重新校验 session，期间禁用保存/切企业；发现变化或无法确认时失效旧表单。服务器不依赖通知可达。

选择企业的响应也有独立代次保护，并要求随后 session 与该次选择返回的 context_id 完全相同；否则要求重新选择，不能把另一个标签的后续选择作为本次选择成功结果。不会自动把旧草稿保存到 B，也不在 context 错误时重试写请求。

仓库 Node 测试门控 HTTP 200 的成功响应，在改变上下文后才释放响应；模拟取消后已完成回调仍到达，覆盖列表、详情、新建、编辑。这是明确标注的传输替身，专门测试生产响应门禁，不把请求失败/数据库超时当作成功竞态。真实 PG 另测无通知时的拒绝及两个锁顺序，真实浏览器另测双标签 UI。

## R2：父记录共享锁

详情首先单独 SELECT 客户 id FOR SHARE，再进行客户版本/计数、联系人、项目、项目人员、地点、内部负责人和角色历史查询。所有查询在该事务内；共享锁持有至读取事务提交。先用独立锁查询再读取 BASE，避免等待更新元组时关联子查询仍使用等待前语句快照。

保存现有客户首先在同一路径 FOR UPDATE 父记录，再整体替换关联、更新版本/历史/幂等结果/审计。新客户插入与关联同事务，不会被读者看到半成品。relations 只由 save 调用；当前没有其他生产关联修改/删除入口，未来增加子项路径必须先取得同一父锁。读者不在读完后修补版本字段。

读先持锁时正常写者等待，读者返回完整旧聚合并提交后写者更新；写先持锁时读者等待提交，再从新的语句读取完整新聚合。该方案不改变事务隔离级别，也无需在身份查询之后才设置快照。实际 PG 测试在 contacts 查询之后暂停读线程，以 pg_blocking_pids 证实正常 save 等待；有限超时和 finally 释放门控防止测试自锁，最终验证旧聚合的版本、计数、引用、地点、内部负责人、历史与新提交版本。

生产模式拒绝和数据库 3 秒 statement_timeout 保留，没有延长超时、吞错或禁用 TLS 来取得通过。
